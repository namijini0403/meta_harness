> 이 파일은 **예시**다 — 복사해 쓰는 파일이 아니다. v2 thin core 템플릿의 플레이스홀더가 실제로 어떻게 채워지는지 보여준다.
> 가상 프로젝트: 초등 영단어 암기 PWA (React+TS / Hono+pg, 교사가 만드는 학급용 앱).

# 단어숲 작업 하네스 — thin core

초등 3~6학년 영단어 암기 PWA. 숲을 가꾸며 단어를 외운다. 모노레포: client(React18+Vite+TS) / server(Hono+pg).
**"단어장 앱"으로 한정짓지 말 것** — 문장·듣기 모듈로 확장 예정.

## 0. 대원칙

(템플릿 그대로 유지 — 이 절은 프로젝트마다 바뀌지 않는 공통 원칙이다.)

## 1. 위험 라우팅

(템플릿 표 그대로 유지. 프로젝트 특화 행이 생기면 추가 — 예: "단어 콘텐츠 대량 저작 → author-words 스킬".)

## 2. 되돌리기 어려운 작업 = 사용자 승인 먼저

DB 구조 변경·데이터 삭제 / 로그인·권한 변경 / 배포 설정 / 비밀키 회전 / git 히스토리 재작성 / **localStorage 키 'wordforest-save' 관련 변경** (실사용 학급 저장 호환).

## 3. 불변식 + 검증 루프 (커밋 전 순서대로 전부 — 위반 = 실패)

- `Math.random()` 금지 → `seedRng(seed)`만. 같은 seed = 같은 퀴즈 (재현성) — vitest 속성 테스트가 강제.
- 단어 데이터는 `content/words/*.md`가 정본, `src/data/`는 AUTO-GENERATED — 직접 수정 금지, `npm run build:words`로 재생성.
- 보기 4개 값 유일·정답 1개. 오답은 실제 혼동 기반(철자 유사·품사 혼동)만.
- 학년 어휘 수준 준수 (교육과정 기본 어휘 목록 밖 단어는 4학년 이하 노출 금지).

```
npx tsc --noEmit -p client && npx tsc --noEmit -p server
npx vitest run                        # 전체 — 부분 실행은 완료 증거가 아님
npm run build -w client
npx tsx scripts/check-word-dupes.ts   # 단어 id 중복 게이트
```
- 테스트 수 기준선: 1,204 (2026-07-08) — 줄어들면 뭔가 깨진 것.

## 4. 불변 결정 (정본 = docs/decisions-log.md)

- localStorage 키 'wordforest-save' 변경 금지 (저장 호환, 2026-07-01).
- 나무 성장 보상은 "하루 첫 학습"에만 — 반복 학습 보상 경로 추가 금지 (과사용 방지, 2026-07-05).
- 이벤트는 화이트리스트 6종만·자유 텍스트/닉네임 금지·ANALYTICS_DB_URL 미설정=no-op은 학부모 동의 전 수집 방지 법적 안전장치 (2026-07-02, db-analytics 팩 설치 시 기입됨).

## 5. 환경·커밋 규약

- Windows + PowerShell. 커밋 메시지 한국어, 큰따옴표 금지(here-string `@'...'@`).
- main 푸시 = Railway 자동 배포. `content/원본자료/`는 저작권 원본 — gitignore, `git add -A` 금지.
- 사용자가 직접 할 일 → `docs/USER-TODO.md`. 실패 기록 → `docs/rationalization-guardrails.md`.

## 6. 토큰 경제

(템플릿 그대로 — 단어 콘텐츠 대량 저작 시 서브에이전트 위임, 4규약 준수. orchestration 팩은 미설치: 1인 프로젝트라 불필요.)

## 7. 자주 쓰는 사실

- 단어 md 형식이 바뀌면 파서(`scripts/word-parser.ts`)와 형식 테스트 둘 다 갱신 — 한쪽만 고치면 빌드는 되고 데이터가 조용히 빠진다.

## 채움 요령 (이 예시에서 볼 것)

1. **§0·§1·§6은 거의 그대로 둔다** — 프로젝트 특화 행만 추가. 코어의 얇음을 지키는 것이 이 템플릿의 존재 이유다.
2. **§3 불변식은 "실제로 깨져본 것"부터** — 상상으로 채우지 말고, init 시점엔 2~3개면 충분. 실패가 나면 자란다.
3. **§3 명령은 실행해본 것만** — 안 도는 명령을 규약에 박으면 첫 커밋부터 하네스 불신.
4. **§2 위험 구역에 프로젝트 특화 항목을 꼭 추가** — 저장 키·법적 게이트처럼 이 프로젝트만의 "되돌리기 어려운 것".
5. **해당 없는 절은 삭제** — 빈 절을 남기지 않는다. §4는 날짜와 함께, "왜"는 decisions-log.md에.
