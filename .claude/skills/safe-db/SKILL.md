# DB 안전 작업 (safe-db)

대상 독자는 AI 모델이다. 사용자는 초보 교사이며 스키마·migration·RLS 같은 용어를 모른다. 이 스킬은 모델이 사용자를 안전하게 안내하도록 지시하는 문서다 — 교사에게 그대로 보여주는 문서가 아니다.

## 절차 (건너뛰기 금지)

1. **현재 상태 파악**: 스키마 변경 전 기존 테이블·데이터 유무를 실제로 조회해서 확인한다 (기억이나 추측으로 판단 금지). 테이블이 비어 있는지, 이미 사용 중인지에 따라 위험도가 달라진다.
2. **위험 분류**: 작업을 시작하기 전 아래 세 등급 중 어디에 해당하는지 스스로 판정한다.
   - **안전(바로 진행 가능)**: 새 테이블 생성, 새 컬럼 추가(NULL 허용 또는 기본값 있음), 새 인덱스 추가, 읽기 전용 조회.
   - **위험(승인 필수)**: 컬럼 삭제, 컬럼 타입 변경, 기존 컬럼에 NOT NULL 제약 추가, 테이블/컬럼 이름 변경, 기존 데이터가 이미 들어있는 테이블에 대한 모든 구조 변경.
   - **금지(사용자의 명시적 확인 없이는 어떤 상황에서도 자동 실행 금지)**: DROP TABLE, TRUNCATE, WHERE 절 없는 DELETE/UPDATE. "빠른 정리", "테스트용이니 상관없다" 같은 판단은 모델이 스스로 내리지 않는다 — 반드시 되묻는다.
3. **백업 또는 개발 환경 우선**: 운영 데이터가 있는 DB에 위험 등급 변경을 가하기 전, 가능하면 개발/테스트 DB에서 먼저 검증한다. 그럴 환경이 없으면 백업(스냅샷·덤프)을 먼저 만든다. 백업 수단 자체가 없는 경우 "지금 이 변경은 실패하면 되돌릴 방법이 없어요"를 사용자에게 먼저 알리고, 그래도 진행할지 물은 뒤에만 실행한다.
4. **가역성 확보**: migration은 되돌리는 방법(롤백 SQL 또는 절차)을 함께 기록해둔다. 되돌릴 수 없는 변경(컬럼 삭제로 인한 데이터 영구 소실 등)은 승인 질문에서 "되돌릴 수 없다"는 사실을 반드시 명시한다. "아마 괜찮을 것"이라는 추측으로 가역성을 판단하지 않는다.
5. **권한 설정은 처음부터**: 새 테이블을 만들 때 RLS(행 단위 보안)나 접근 권한 정책을 테이블 생성과 같은 작업 단위로 함께 설정한다. "일단 열어두고 나중에 잠그자"는 하지 않는다 — 그 사이 시간에 실제로 공개 노출 사고가 난다.
6. **실행**: 안전 등급은 바로 진행. 위험/금지 등급은 3~5단계를 마친 뒤 승인을 받고 나서야 실행한다.
7. **완료 검증**: migration 명령이 에러 없이 끝났다는 것은 완료가 아니다. 실제로 값을 하나 써보고(INSERT), 다시 읽어서(SELECT) 기대한 값이 맞는지 확인해야 완료다. 컬럼을 바꿨다면 기존 데이터가 여전히 읽히는지도 함께 확인한다.

## 흔한 실수 사례

- "학생 이름 컬럼을 text에서 varchar(20)으로 바꿔줘" 같은 요청은 타입 변경이므로 위험 등급이다. 20자를 넘는 기존 이름이 있으면 데이터가 잘리거나 migration이 실패할 수 있다는 것을 먼저 확인·고지한다.
- "이 테이블 안 쓰는 것 같으니 지워줘"는 모델의 추측이다. 실제로 참조하는 코드가 있는지 검색으로 확인하기 전에는 DROP을 실행하지 않는다.
- 새 테이블을 만들면서 권한 정책을 빼먹고 "나중에 추가하겠다"고 메모만 남기는 것은 5번 위반이다.
- 외래키(참조) 관계가 있는 테이블을 지울 때 "이 테이블만 지우면 된다"고 판단하지 않는다. 다른 테이블이 이 데이터를 참조하고 있으면 함께 깨질 수 있으므로 참조 관계부터 확인한다.
- 여러 개의 위험 변경을 한 번에 묶어서 "한꺼번에 승인받자"고 하지 않는다. 서로 다른 테이블·다른 성격의 변경이면 사용자가 각각 무엇을 잃는지 구분해서 이해할 수 있도록 나눠 설명한다.

## 완료 전 체크리스트

- [ ] 변경 대상 테이블에 기존 데이터가 있는지 실제로 조회해 확인했는가.
- [ ] 위험/금지 등급이면 사용자에게 결과 중심으로 설명하고 승인을 받았는가.
- [ ] 백업 또는 개발 환경에서 먼저 검증했는가, 못 했다면 그 사실을 알렸는가.
- [ ] 새 테이블이면 권한(RLS) 정책을 함께 넣었는가.
- [ ] 실제 INSERT/SELECT로 왕복 확인했는가.

## 다른 스킬과의 관계

- 로그인한 사용자별로 접근 범위를 나누는 테이블이면 auth-basics의 서버 측 권한 검사 원칙과 함께 적용한다.
- 학생 식별 정보가 포함된 테이블이면 student-privacy의 최소 수집·별명 원칙을 먼저 확인한 뒤 스키마를 설계한다.
- 변경 사항을 배포와 함께 내보낼 때는 deploy-check의 배포 전 점검 절차로 이어간다.

## 사용자에게 말할 때

- 전문 용어(스키마, migration, RLS, 트랜잭션) 대신 결과로 설명한다: "이 컬럼을 지우면 지금까지 학생들이 입력한 답이 사라져요. 계속할까요?"
- 승인 질문은 되돌릴 수 없는 단계 앞에서만, 한 번에 쉬운 말로 묻는다. 안전 등급 작업까지 매번 승인을 구해 사용자를 피로하게 만들지 않는다.
- 위험을 알릴 때는 "왜 위험한지"(기술적 이유)가 아니라 "무엇을 잃는지"(결과)를 먼저 말한다.

## 합리화 방지

| 유혹 | 규율 |
|---|---|
| "컬럼 하나 지우는 거니 그냥 실행" | 기존 데이터가 있으면 무조건 승인 필수 (2번). |
| "migration 명령이 성공했으니 끝" | 실제 쿼리로 왕복 확인 전엔 미완료 (7번). |
| "나중에 권한 설정하면 되지" | RLS/권한은 테이블 생성과 동시에 (5번) — 공개 노출 사고 예방. |
| "테스트 환경이니 TRUNCATE 정도는 괜찮을 것" | 운영/개발 여부와 무관하게 금지 목록은 명시적 확인 필수 (2번). |
