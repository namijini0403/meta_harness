# 커밋 전 검증 (verify)

CLAUDE.md §3의 검증 루프를 **순서대로, 전부** 실행한다. 하나라도 실패하면 커밋 금지 — 고치고 처음부터 재실행. 단 게이트의 **규모**는 아래 위험 비례 원칙에 따라 정한다 — "전부"는 항상 지키되 "얼마나 넓게"는 변경의 위험에 비례한다.

## 게이트 규모는 변경의 위험에 비례한다

- **문구·스타일·주석만 변경**: 타입체크+빌드는 항상 실행한다. 테스트는 관련 스모크로 축소할 수 있다. 단 가드 두 가지는 필수다: ① 축소 실행 커밋이 연속되면 그다음 일반 커밋에서는 전체 스위트가 필수다 — 부분 실행이 누적되는 것이 회귀를 은폐하는 고전적 경로다. ② 테스트 스위트가 애초에 빠르면(수십 초 수준) 축소하지 말고 그냥 전체를 돌리는 것이 기본이다 — 축소는 느린 스위트에서만 쓰는 예외지 습관이 아니다.
- **일반 기능 변경**: 전체 테스트+타입체크+빌드 (현행 절차 그대로, 아래 1~5번).
- **고위험 변경(CLAUDE.md §2 해당 — DB 구조·인증/권한 체계·배포 설정·비밀키·git 히스토리 재작성 등)**: 전체 스위트+실제 구동 확인+risk-review 스킬 연계(신선한 검토자의 독립 검증).
- **배포가 동반되는 변경**: 전체 스위트+실배포 스모크(deploy-check 스킬 연계) — 푸시는 완료가 아니다.

## 절차

1. **게이트 실행** (위 규모 분류에 따라, CLAUDE.md §3의 명령을 순서대로):
   - 타입체크 → 테스트(규모에 맞게) → 빌드 → 추가 게이트
   - ⚠️ 규모 분류 없이 임의로 축소한 실행(`-t` 필터 등)은 통과가 아니다. 축소는 위 표의 조건을 만족할 때만 유효하고, 그 외에는 전체 실행이 정본.
2. **기준선 대조**: 기준선 정본은 원칙적으로 **테스트 러너/CI 산출물**(테스트 실행 로그의 합계, CI 대시보드 등 자동 산출 수치)이다. CLAUDE.md §3에 수기로 적힌 숫자는 **자동 산출 수단이 없는 프로젝트에서만** 정본으로 쓰고, "정본 = 상태판"이라 적혀 있으면 해당 마스터플랜 상태판을 본다. 대조해서 **줄었으면** 뭔가 깨진 것 — 원인 규명 전 커밋 금지. 늘었으면 정본을 갱신.
3. **임시 파일 청소**: 검증용 임시 테스트·덤프 파일 전부 삭제 확인 (`git status`로 의도치 않은 파일 확인).
4. **런타임 확인** (제품 코드 변경 시): 테스트 통과 ≠ 동작. 변경된 흐름을 실제로 한 번 구동해 눈으로 확인.
   - **UI 변경이면 브라우저에서**: 변경 화면을 실제 조작(클릭·입력)으로 여정 끝까지 + 콘솔 에러 0 + 스크린샷 육안(데스크톱·모바일 뷰포트). e2e-deploy 팩 사용 시 상세 규약 = `docs/browser-verification.md`(모드 ②), 없으면 수동으로라도 — 말없이 생략 금지.
   - **배포를 동반하면**: 푸시 = 완료가 아니다 — `docs/deploy-verification-loop.md`(배포 대기 폴링 + 배포본 스모크) 통과 후에만 "배포 완료" 보고.
5. **커밋**: CLAUDE.md §5 규약(메시지 언어·따옴표 규칙·Co-Authored-By·명시 경로 add — `git add -A` 금지).

## 합리화 방지

| 유혹 | 규율 |
|---|---|
| "내 부분만 테스트 돌려서 통과했다" | 규모 분류상 축소가 허용된 경우가 아니면 전체 실행만 정본. |
| "테스트가 통과했으니 동작한다" | 제품 코드 변경은 실제 구동 확인까지. |
| "급하니 빌드는 생략" | 규모와 무관하게 타입체크+빌드는 항상. 생략 = 미검증 커밋. |
| "테스트 수 줄었지만 내 작업과 무관할 것" | 원인 규명 전 커밋 금지. |
| "축소 실행이 편하니 계속 축소" | 연속 축소 커밋 다음엔 전체 스위트 필수, 스위트가 빠르면 애초에 축소 금지. |
