# 인증·로그인 안전 (auth-basics)

대상 독자는 AI 모델이다. 사용자는 초보 교사이며 해시·세션·JWT 같은 용어를 모른다. 이 스킬은 모델이 안전한 선택을 기본값으로 삼아 초보 사용자를 안내하도록 지시하는 문서다.

## 절차

1. **직접 구현 금지**: 비밀번호 해싱·세션 관리·토큰 발급 로직을 처음부터 직접 짜지 않는다. 프로젝트에 이미 관리형 인증(Supabase Auth, Firebase Auth, Clerk, NextAuth 등)이 있으면 그것을 우선 사용한다. 없으면 도입을 먼저 제안한다. 사용자가 그래도 자체 구현을 원하면, 직접 만든 암호화 함수는 절대 쓰지 않고 검증된 표준 라이브러리(bcrypt, argon2 등)만 사용한다.
2. **평문 저장 절대 금지**: 비밀번호를 원문 그대로 DB·로그·에러 메시지·이벤트에 남기는 코드는 어떤 경우에도 작성하지 않는다. 기존 코드에서 평문 저장을 발견하면 작업 우선순위와 무관하게 즉시 사용자에게 알리고 수정을 제안한다.
3. **권한 검사는 서버에서**: "선생님만 보이게", "학생은 이 페이지 못 들어가게" 같은 요청은 화면(버튼 숨김, 메뉴 제거)만으로 처리하지 않는다. 서버(API 응답 또는 DB 접근 정책) 쪽에서도 반드시 같은 검사를 반복한다. 클라이언트에서 숨기는 것은 사용성 개선일 뿐 보안 조치가 아니라는 점을 사용자에게도 짧게 알린다.
4. **아동 사용자 개인정보 최소화**: 학생이 직접 로그인하는 구조를 만든다면 이름·이메일 등 꼭 필요한 항목만 수집한다. 자세한 기준은 student-privacy 스킬을 함께 참고한다.
5. **기존 인증 체계 변경은 위험 구역**: 이미 동작 중인 로그인 방식을 바꾸는 작업(인증 제공자 교체, 세션 저장 방식 변경, 비밀번호 정책 강화, 토큰 만료 시간 변경 등)은 전체 사용자가 한꺼번에 로그아웃되거나 로그인이 막힐 수 있다. 이 위험을 진행 전 반드시 쉬운 말로 알리고 승인을 받는다. "일부 사용자에게만 영향"이라는 판단도 모델이 확신 없이 내리지 않는다.
6. **완료 검증**: 코드가 에러 없이 컴파일/실행된다는 것은 완료가 아니다. 다음 두 가지를 실제로 수행해야 완료다.
   - 정상 계정으로 실제 로그인을 시도해 성공하는지 확인.
   - 권한이 없는 계정 또는 로그아웃 상태로 보호된 화면·기능에 실제로 접근을 시도해, 정말로 차단되는지 확인. "코드상 막혀 있어 보인다"는 근거가 아니다.

## 흔한 실수 사례

- "관리자 페이지는 링크를 안 보여주면 되지 않나요?"라는 요청을 그대로 구현하면 URL을 직접 입력하는 사람을 막지 못한다. 반드시 서버 쪽 검사를 함께 추가한다.
- 소셜 로그인(구글 등)을 새로 추가하면서 기존 이메일 로그인 사용자의 세션을 함께 무효화하는 변경은 5번 위반 — 영향 범위를 먼저 확인하고 알린다.
- "테스트 계정 비밀번호는 그냥 콘솔에 찍어서 확인하자"는 2번 위반이 될 수 있다. 로그에 실제 비밀번호 문자열이 남지 않게 주의한다.
- "비밀번호 찾기" 기능을 만들며 실제로는 비밀번호를 이메일로 그대로 보내는 방식을 택하면 어딘가에 평문 비밀번호를 저장해야 하므로 2번 위반이다 — 재설정 링크 방식을 쓴다.
- 관리자 권한을 코드 상수(예: 특정 이메일 문자열 하드코딩)로만 구분하면 실수로 잘못된 계정에 권한이 부여되기 쉽다. 역할(role) 정보를 DB에 명시적으로 저장하고 서버에서 조회하는 방식을 우선한다.

## 완료 전 체크리스트

- [ ] 비밀번호·토큰이 평문으로 어디에도(DB·로그·에러 메시지) 남지 않는가.
- [ ] 권한 검사가 서버(API/DB 정책) 쪽에도 존재하는가, 클라이언트 숨김에만 의존하지 않는가.
- [ ] 기존 인증 체계를 바꾸는 작업이라면 영향받는 사용자 범위를 사용자에게 알리고 승인받았는가.
- [ ] 정상 계정 로그인 성공을 실제로 확인했는가.
- [ ] 권한 없는 접근이 실제로 차단되는지 시도해봤는가.

## 다른 스킬과의 관계

- 학생이 로그인 주체라면 student-privacy의 최소 수집 원칙과 함께 적용한다.
- 사용자·권한 테이블을 새로 만들거나 바꾸는 작업이면 safe-db의 위험 분류·백업 절차를 함께 따른다.
- 인증 관련 변경을 배포할 때는 deploy-check에서 "기존 로그인 세션에 영향이 있는지"를 배포 전 점검 항목에 포함한다.

## 사용자에게 말할 때

- "해시", "세션 토큰" 대신 "비밀번호를 안전하게 저장하는 방식", "로그인 상태를 기억하는 방법"처럼 풀어 말한다.
- 기존 로그인 방식을 바꿀 때는 "이 작업을 하면 지금 로그인해 있는 선생님들이 다시 로그인해야 할 수 있어요" 식으로 결과를 먼저 알린다.
- 승인은 위험 구역(5번) 진입 전에만 묻는다. 일반적인 기능 추가까지 매번 승인을 구하지 않는다.

## 합리화 방지

| 유혹 | 규율 |
|---|---|
| "간단한 프로젝트니 비밀번호 직접 암호화" | 검증된 라이브러리/관리형 인증만 (1번). |
| "화면에서 메뉴만 숨기면 충분" | 서버 검사 없으면 미완료 (3번). |
| "코드 다 짰으니 완료" | 실제 접근 시도로 차단 확인 전엔 미완료 (6번). |
| "이번 변경은 영향이 작을 것" | 기존 인증 체계 변경은 항상 승인 필수 (5번). |

상세 검증 원칙은 CLAUDE.md §3, 데이터 최소화는 student-privacy 스킬 참조.
