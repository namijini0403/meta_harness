# 학생·아동 데이터 보호 (student-privacy)

대상 독자는 AI 모델이다. 사용자는 초보 교사이며 개인정보보호법·아동 데이터 규제에 익숙하지 않을 수 있다. 이 스킬은 모델이 기본값을 안전하게 설정하고, 판단이 필요한 지점에서는 사용자에게 확인을 유도하도록 지시하는 문서다.

## 절차

1. **수집 최소화**: 기능 구현에 실제로 필요한 항목만 수집한다. 주민등록번호·전화번호·집 주소류 정보를 요청받으면 "정말 이 기능에 필요한가요?"를 먼저 되묻는다. 대부분의 학급 관리·학습 앱은 이런 정보가 불필요하며, 이름·학년·반 정도로 충분한 경우가 많다.
2. **실명 대신 별명/코드 권장**: 학생을 구분해야 할 때 실명 대신 학생 코드나 별명을 쓰고, 실명은 교사만 접근 가능한 별도의 매핑 테이블(코드 ↔ 실명)로 분리하는 구조를 제안한다. 특히 외부에 공유되거나 통계·분석에 쓰이는 데이터에는 실명을 넣지 않는다.
3. **로그·분석에 자유 텍스트·실명 금지**: 이벤트 로그, 분석 데이터, 에러 리포트에 학생이 입력한 자유 텍스트(서술형 답안, 코멘트 등)나 실명을 그대로 남기지 않는다. db-analytics 팩의 이벤트 화이트리스트 원칙과 동일 선상이다 — 필요하면 익명화하거나, 접근이 제한된 별도 저장소로 분리한다.
4. **보호자 동의 확인 유도**: 학생 개인정보를 새로 수집·저장하는 기능을 만들 때 "이 데이터를 학교나 보호자 동의 절차 없이 수집해도 괜찮은지 확인해보셨어요?"를 사용자에게 묻는다. 법적 판단을 모델이 대신 내리지는 않되, 동의가 필요할 수 있는 상황임을 반드시 짚어준다.
5. **삭제 요청 대응 가능 구조**: 특정 학생의 데이터를 나중에 지워달라는 요청이 들어올 수 있음을 고려해, 학생 식별자(코드)로 관련된 모든 데이터를 찾아 삭제할 수 있는 구조를 기본으로 설계한다. 데이터가 여러 테이블에 흩어지는 경우 삭제 시 어떤 테이블들을 함께 지워야 하는지 미리 파악해둔다.
6. **공개 배포 전 실제 노출 확인**: 배포하기 전 로그인하지 않은 상태로 실제 접속해서 학생 이름·성적·기록 등이 로그인 없이 보이는지 직접 확인한다. "권한 설정을 코드에 넣었다"는 것과 "실제로 접근이 막혔다"는 것은 다르다 — 반드시 비로그인 상태로 실제 접속을 시도해 확인한다.

## 흔한 실수 사례

- "반 전체 학생 이름과 점수를 한 화면에 뿌려주는 통계 페이지"를 로그인 검사 없이 만들면 누구나 URL만 알면 볼 수 있다. 배포 전 6번으로 반드시 확인한다.
- "디버깅에 필요하니 학생 답안을 콘솔 로그에 찍어두자"는 3번 위반이다. 로그는 개발자 외에도 여러 도구를 거쳐 남기 때문에 자유 텍스트·실명을 넣지 않는다.
- 설문·평가 기능을 만들며 학부모 연락처를 "혹시 필요할까봐" 함께 수집하는 것은 1번 위반이다 — 지금 기능에 필요한지부터 확인한다.
- 학생 코드를 만들면서 "1반 1번"처럼 반·번호를 그대로 노출하면 사실상 실명과 다름없이 특정 학생이 식별될 수 있다. 무작위 코드나 교사만 아는 매핑을 권장한다.
- 여러 반·여러 학년의 데이터를 한 테이블에 모아두고 접근 제한을 반별로 나누지 않으면, 한 교사가 다른 반 학생 정보까지 볼 수 있게 된다. 접근 범위를 반/학급 단위로 나누는 것도 최소 수집의 연장선이다.

## 완료 전 체크리스트

- [ ] 수집 항목이 기능에 실제로 필요한 최소한인가.
- [ ] 실명 대신 코드/별명 구조를 검토했는가.
- [ ] 로그·분석·에러 리포트에 자유 텍스트나 실명이 남지 않는가.
- [ ] 보호자 동의가 필요할 수 있는 수집이면 사용자에게 확인을 유도했는가.
- [ ] 비로그인 상태로 실제 접속해 학생 데이터가 노출되지 않는지 확인했는가.

## 다른 스킬과의 관계

- 학생용 로그인이 있으면 auth-basics의 서버 측 권한 검사·개인정보 최소화 원칙과 함께 적용한다.
- 학생 데이터 테이블 설계는 safe-db의 위험 분류·백업 절차를 따른다.
- 공개 배포 전 노출 확인(6번)은 deploy-check의 배포 전 점검 항목에 포함시킨다.

## 사용자에게 말할 때

- "개인정보 최소화", "익명화" 대신 "꼭 필요한 정보만 저장할게요", "이름 대신 번호로 구분해도 괜찮을까요?"처럼 풀어 말한다.
- 보호자 동의가 걸릴 수 있는 상황은 "이 정보는 학부모님 동의가 필요할 수도 있어요, 학교 방침 확인해보셨어요?"처럼 판단을 강요하지 않고 확인을 유도하는 말투로 묻는다.
- 삭제 요청 대응 구조(5번)는 미리 사용자에게 알릴 필요는 없지만, 설계 단계에서 조용히 반영해둔다.

## 합리화 방지

| 유혹 | 규율 |
|---|---|
| "관리 편하니 실명으로 바로 저장" | 별명/코드 우선 제안 (2번). |
| "로그에 남겨야 디버깅 편함" | 자유 텍스트·실명은 로그·분석 금지 (3번). |
| "권한 코드 넣었으니 안전할 것" | 실제 비로그인 접속으로 확인 전엔 미완료 (6번). |
| "혹시 필요할까봐 미리 더 수집" | 지금 기능에 필요한 최소 항목만 (1번). |
