# 비밀값 관리 (secrets-basics)

대상 독자는 AI 모델이다. 사용자는 초보 교사이며 "환경 변수", "커밋", "버전 관리"가 무엇인지 모를 수 있다. 이 스킬은 모델이 키 유출을 구조적으로 막도록 지시하는 문서다.

## 절차

1. **키를 받기 전에 먼저 준비**: 사용자가 API 키를 붙여넣기 전에 `.env`(또는 프로젝트 표준 비밀값 파일)와 `.gitignore`에 그 파일이 포함돼 있는지 먼저 확인·생성한다. 순서가 중요하다 — 키를 받고 나서 뒤늦게 gitignore를 추가하면 그 사이에 이미 코드나 커밋에 박아 넣었을 위험이 있다.
2. **하드코딩 금지**: API 키·비밀번호·토큰 문자열을 소스 코드에 직접 쓰지 않는다. 반드시 환경 변수나 비밀값 파일을 통해 읽는다. 기존 코드에서 이런 문자열을 발견하면(모델이 자동 감지했을 때도) 작업 목적과 무관하게 즉시 환경 변수로 옮기도록 제안한다.
3. **키 종류 구분**: 클라이언트(브라우저)에 노출돼도 되는 키(예: Supabase anon/public key)와 서버에서만 써야 하는 키(예: service role key, 결제 시크릿 키)를 구분해서 안내한다. 서버 전용 키를 클라이언트 코드나 프론트엔드 번들에 절대 넣지 않는다. 어느 쪽인지 확실하지 않으면 발급 문서를 확인하거나 사용자에게 물어본다.
4. **이미 커밋된 경우**: git 이력에서 해당 파일을 지우는 새 커밋을 만들어도 과거 커밋 기록에는 키가 그대로 남아 있어 유출이 해소되지 않는다는 것을 사용자에게 명확히 알린다. 진짜 해법은 **키 회전(발급처 대시보드에서 기존 키 폐기 + 새 키 발급)**이며, 이것 없이는 "삭제했으니 안전해졌다"고 완료 보고하지 않는다.
5. **배포 환경에는 대시보드로**: 배포할 때 `.env` 파일을 그대로 서버에 올리거나 저장소에 커밋하지 않는다. 배포 플랫폼(Vercel, Railway 등)의 환경 변수 설정 화면에 값을 직접 등록하도록 안내한다.
6. **완료 검증**: "환경 변수로 옮겼다"고 말한 것과 "코드에 실제로 남은 키 문자열이 없는 것"은 다르다. git grep 등으로 실제 검색해서 남은 흔적이 없는지 확인한 뒤에만 완료로 보고한다.

## 흔한 실수 사례

- ".env.example 파일에 실제 키 값을 그대로 적어넣는 것"은 1~2번 위반이다. 예시 파일에는 빈 값이나 더미 값만 넣는다.
- "테스트니까 잠깐 코드에 키를 넣고 나중에 지우자"는 실수로 커밋될 위험이 크다 — 처음부터 환경 변수로 시작한다.
- Supabase의 anon key를 "비밀값이니 숨겨야 한다"고 오해해 필요한 클라이언트 기능을 막는 것도 실수다 — 3번을 참고해 어떤 키가 실제로 서버 전용인지 구분한다.
- 채팅·스크린샷·에러 리포트에 사용자가 키를 그대로 붙여넣었을 때, 이를 그대로 코드에 옮겨 적는 과정에서 커밋 대상 파일에 함께 남기지 않도록 주의한다.
- 여러 서비스(결제, 이메일, DB)의 키를 한 파일에 몰아넣고 이름을 구분 없이 적으면 어떤 키가 서버 전용인지 헷갈려 실수로 클라이언트에 노출시키기 쉽다. 키 이름에 용도를 명확히 남긴다.

## 완료 전 체크리스트

- [ ] `.gitignore`에 비밀값 파일이 포함돼 있는가.
- [ ] 코드 어디에도 키 문자열이 직접 적혀 있지 않은가 (git grep으로 확인).
- [ ] 서버 전용 키가 클라이언트 번들에 포함되지 않았는가.
- [ ] 이미 유출된 적이 있는 키라면 회전(재발급)을 완료했는가.
- [ ] 배포 환경 변수에도 값이 등록됐는가.

## 다른 스킬과의 관계

- 배포 직전에는 deploy-check의 배포 전 점검 항목으로 이 스킬의 절차를 다시 한 번 수행한다.
- 인증 관련 키(예: 관리형 인증의 service key)를 다룰 때는 auth-basics의 키 종류 구분 원칙과 겹치므로 함께 확인한다.

## 사용자에게 말할 때

- "환경 변수"가 낯설면 "코드에는 안 적고 따로 안전한 곳에 보관하는 설정값"이라고 풀어 말한다.
- 키가 이미 유출됐을 가능성이 있으면 "이 키는 이미 공개된 것으로 봐야 해요, 서비스에서 새 키를 발급받아야 해요"처럼 결과 중심으로 알린다.
- 승인이 필요한 순간: 회전이 필요한 키가 발견됐을 때, 배포 전 점검에서 유출 흔적을 찾았을 때. 이때는 "지금 바로 이 키를 새로 발급받는 게 좋아요, 안내해드릴까요?"처럼 다음 행동을 제안한다.

## 합리화 방지

| 유혹 | 규율 |
|---|---|
| "일단 키 받고 나중에 .env로 옮기자" | gitignore·env 파일 준비가 먼저 (1번). |
| "삭제 커밋했으니 유출 해결" | git 이력엔 남는다 — 키 회전 필요 (4번). |
| "코드에 안 보이니 안전할 것" | git grep으로 실제 확인 전엔 미완료 (6번). |
| "이 키는 그냥 anon key니 대충 다뤄도 될 것" | 키마다 노출 허용 범위가 다르므로 항상 종류를 먼저 구분 (3번). |
